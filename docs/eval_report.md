# 평가 리포트 (6회차 선택 과제)

> 기준 파일: `results/compare.csv` · `judge_calibration.json` · `judge.json` · `calc_e2e.json`.
> 전부 2026-10-13 재발급 키로 실제 모델(gpt-5.4-mini + nano)을 돌린 결과다. 전체 코퍼스 51문서 3,695청크.
> 40문항 agentic: Recall@1 65.0% · Recall@5 85.0% · MRR 0.734 · 답변률 95% · 오거절률 5.3% · 미답변 정확도 1.0 · 평균 11.8초 · p95 22.6초.

## 1. 3단계 비교 (`make compare`, Recall@5 · MRR 유형별)

- **메타데이터형이 가장 많이 올랐다.** MRR 50.0% (baseline) → 45.0% (hybrid) → 100.0% (agentic), Recall@5 60% → 60% → 100%. "2013년판", "2019.07 상품설명서" 같은 조건은 검색기를 바꿔도 안 풀리고(hybrid 에서 오히려 내려갔다), Self-Query 가 `effective_on`·`doc_type` 필터를 뽑아 판본을 가려 주자 5문항 전부 1등이 됐다. 4회차 ADR-003 의 "되돌릴 조건" 마지막 줄이 실제로 그렇게 됐다.
- **조항번호형은 agentic 에서 내려갔다.** Recall@5 100% → 87.5% → 75.0%, MRR 75.0% → 83.3% → 59.4%. 세 단계 중 유일하게 끝까지 하락한 유형이다. 원인은 둘로 보인다. rewrite 노드가 "제34조에 따르면"을 자연어로 풀어 쓰면서 조항번호 토큰의 BM25 가중이 약해지고, 필터가 `doc_type=약관` 처럼 넓게 잡히면 같은 발행사의 다른 판본 조항이 같이 올라온다(S03 하나은행 2013·2024 판 혼재). 조항번호가 질문에 있으면 **재작성하지 않고 원문 그대로 검색**하는 분기가 다음 판의 첫 수정이다.
- **미답변형이 0 → 50% (Recall@5), 미답변 정확도 1.0.** baseline·hybrid 는 거절 개념이 없어 0 이었고, agentic 은 S39·S40 둘 다 `insufficient` 로 한계를 밝혔다. 다만 오거절 2건(S04 예금거래기본약관 질권, S28 분쟁조정사례)이 생겼고 둘 다 필터가 `doc_type` 을 틀리게 뽑아 0건 → 완화 → 엉뚱한 문서로 간 경우다. 계산형(MRR 30% → 80% → 80%)과 표수치형(72% → 83% → 92%)은 꾸준히 올랐다.

## 2. judge 와 사람이 가장 어긋난 문항 (`results/judge_calibration.json`, n=17)

- **S20 (iM뱅크 인지세 표), judge 0/6 vs 사람 4/6, 차이 −4.** 사람은 근거 일치 2 · 수치 0 · 근거 밖 주장 없음 2 를 줬고 judge 는 셋 다 0 을 줬다. 어긋난 항목은 `basis_match` 와 `no_extra_claim`. judge 가 **박했다**. 이유를 보면 "정답 근거와 다른 금액(35만원/17만5천원)을 제시했고 gold 인용 조항도 맞지 않는다"인데, 사람은 같은 문서의 인지세 표를 인용한 것을 근거 일치로 쳤고 틀린 금액을 수치 항목(0)에서만 깎았다. judge 는 **값이 틀리면 근거도 틀렸다고 연쇄로 깎는다.** 17문항 전체로 보면 `numeric_ok` 는 완전 일치 100%, `basis_match` 88% 인데 `no_extra_claim` 만 35%(MAE 1.12)라, judge 가 못 보는 것은 수치가 아니라 "이 문장이 인용 범위 안인가"다. 루브릭의 `no_extra_claim` 1점 기준("애매한 일반론이 섞임")을 예시 두 개로 더 좁혀 주는 것이 캘리브레이션의 다음 손질이다. judge − 사람 평균 −1.18 로 방향은 일정하게 박한 쪽이다.

## 3. 계산 틀린 문항 (`results/calc_e2e.json`, 15문항 중 9 맞음)

- **C07 iM뱅크 가계대출 연체이자, 기대 803,333원, 결과 0원, `how`="값이 다름".** 함수가 아니라 **추출이 틀렸다.** 같은 함수(`delinquency_interest`)는 `tests/test_calc_golden.py` 에서 같은 입력으로 803,333 을 돌려주고, 이 문항은 재검색 0회·판정 sufficient 로 8초 만에 끝나 LLM 이 자신 있게 파라미터를 넘겼다. 그런데 결과가 정확히 0 인 것은 연체금액 또는 연체일수 중 하나가 0 으로 들어갔다는 뜻이다. 질문의 "월이자 50만원을 2개월 연체"에서 extract 노드가 연체 원금(=월이자 50만원)을 못 잡고 0 으로 둔 것이 가장 그럴듯하다. 틀린 값이 그대로 답변에 실렸으므로 **파라미터가 0 이면 계산하지 않고 되묻는 가드**를 `calc_node` 에 넣는 것이 수정이다.
- 참고로 "계산 안 함" 5건 중 C01~C03(적금 중도해지이율)은 추출이 "적용률을 문서에서 찾지 못했다"고 멈춘 것이고, C13 은 비공개 산출방법서 영역이라 거절한 것이 맞다. 함수 자체가 틀린 문항은 없었다.
